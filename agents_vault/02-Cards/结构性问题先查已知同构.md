# 结构性问题先查已知同构

## 定义

遇到**结构性/设计性问题**（编号、协调、同步、权限边界等跨项目反复出现的问题形状），**默认它已被解决**，先去拿成熟方案、再按自身约束裁剪——而不是即兴造一个。依据是一个双重不足：**AI 复用成熟经验的意识弱，重复造轮子的能力也不足**。即兴草图不是「可能撞对的赌博」，而是**可靠更差的劣化部分重造**。

## 核心

### 前提：为什么默认「已被解决」（Owner 2026-11-15 纠正）

- **重叠是基线，不是成就**：结构性问题被解决过太多次、解空间早被踏遍，任何合理草图几乎必然与某成熟方案重叠。所以「和业界重叠」近乎确定，不值得叫「撞对」；该惊讶的是没重叠，而非重叠。
- **即兴产出的是劣化部分重造**：草图通常只含成熟方案的某个碎片，缺边缘情形定位、缺排除论证、缺边界。实证（corr-47）：即兴只有「前缀」碎片，缺复制卡身份定位（会断 re-sync 的近失错误）、缺「无需中央注册」边界。
- **故纪律不是「赌一把 hoping 撞对」，而是「默认已解决，去拿成熟版，别信即兴」**。把重叠当运气是自我美化；真相是重造可靠地更差。

### 三步（拿到成熟版之后）

1. **识别问题形状，而非表面特征**：剥掉项目专有名词，描述结构。例：「副库卡片编号」→「多自治节点各自编号、偶尔跨节点移交」——该形状与 Jira/GitHub/DOI 同构，不是本项目独有问题。
2. **列标准解法空间 + 按约束排除**：把该形状的已知解法列出，用自身硬约束逐一排除，**排除理由写下来**。例（分布式 id）：内容寻址（Git SHA）——卡可变，排除；中央计数器——离线优先，排除；UUID——丢可读序号，排除；命名空间前缀 + 移交换号（Jira/GitHub）——契合，采纳。
3. **用同构给边缘情形定位**：标准解法自带边缘情形的 principled 定位，常能挡住自己想不到的设计错误。例：「复制卡保留原 id」在同构里 =「fork 保留上游 commit hash / vendored 依赖保留原 import path」——是**上游身份引用，不是本库铸造**→ 推出 `provenance: copied` 豁免设计。缺这层容易设计成「所有卡必须带前缀」→ 给复制卡改号 → 断掉 re-sync 与溯源（真实差点走错处）。

### 为什么值得

- **排除论证**：即兴草图答不了「为什么不是 X」；排除链把补丁变可辩护决策。
- **防边缘设计错误**：同构定位暴露盲点（上例复制卡即真实近失）。
- **防过度设计**：同构告诉你边界在哪。例：前缀撞车无需中央注册——GitHub `owner/repo#123` 表明限定引用 + 边界检查即够，撞车只在移交时暴露，而那正是验收该管的事。

### 时序纪律：检索在设计前，审查不能替代（2026-11-25 补）

同构检索是**设计立项时**的必装目标项（消费者/设计任务），不是事后审查（审核者任务）能补救的：审查沿已裁框架走，框架本身若是即兴劣化重造，审查只能修细节不能换框架。编排方给设计类任务书**必装同构检索目标项**，漏装即编排失职。实证（log-2026-11-25-02）：载体裁断中编排方漏装事前检索，消费者盲检索与审核者沿框架审查各偏一路，靠第三方实物核实才收敛——三路合流的成本本可由事前一次检索避免。

### 边界（何时查、何时不查）

- **查**：结构性、跨项目反复出现、带协调/边界语义的问题（编号/同步/权限/合并）。
- **不查**：一次性局部修补、纯项目业务逻辑——检索成本大于收益。
- **警惕假同构**：表面相似 ≠ 结构相同。映射前核对关键约束是否一致（若 TTL 卡不可变，内容寻址才是正解——排除链本身就是同构校验）。

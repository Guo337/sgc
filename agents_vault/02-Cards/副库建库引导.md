# 副库建库引导（主库赋能新项目 Agent）

## 定义

一个新项目的 Agent 来读本主库（TTL Alpha 内核），如何据此建起属于自己项目的副库。本卡是**赋能入口**：给一条已用真实试建验证过的可走路径，不是理论设计。主库当前整体即「内核」（带第一个平台代码，不纯化）；副库复制其库无关骨架，装自己的项目内容。

## 核心

### 前提事实（实测，非假设）

- **脚本已库无关**：`ttl_locator` 认库根只看三件套（`00-ROOT.md` + `01-Specs/` + `90-Meta/schema.yaml`），支持 `--vault` / `TTL_VAULT` / 向上查找，**零硬编码路径**。复制到任何新目录原样能跑。
- **doctor 对新库的要求明确可满足**：三件套 + 每文件 frontmatter 合规 + id 唯一 + 从 ROOT 可达 + L2 卡有边。空库（无日志无卡）也能 0 ERROR。
- **真实难点不是复制，是裁剪引用闭包**：主库 Specs/SH/卡里含指向 memory-lib 私货的 wikilink（修订指针 `[[corr-…]]`、调研卡、源日志）。直接复制会断链。

### 第 0 步：探活 + 链接通道优先（务必先做，corr-2026-11-15-43）

**不探活直接默认离线 = 漂移；探活后未经 Owner 批准自行离线 = 越权降级**（SPEC-READ v0.7.6 降级前置义务 + D33）。

1. **探活**：查 Obsidian App 在不在跑——`obsidian version` / REST `127.0.0.1:27123` / MCP 工具表。
2. **读主库走链接通道**：主库已注册，用 MCP `vault_read`（拿 links/backlinks）/ `search_simple`，或官方 CLI；**别 view/grep 磁盘读**（绕开 SH 路由/反链）。
3. **副库同样可能被索引**：若你的工作区已被 Obsidian 管辖（obsidian.json 注册），你在底下建的副库子目录**也被索引**——链接通道可用，`--use-cli` 对账跑得起来。**先核实，别假设「副库无 App 绑定」**（项目 Agent 曾误判，实测推翻）。
4. **离线是例外且须 Owner 批准（D33）**：仅当探活+自启证明主通道确不可用、**并向 Owner 呈报获批准**才退离线；未获批准停在链接通道尝试、如实报告，不擅自磁盘读知识。doctor 对已索引库默认 `--use-cli`。

### 建库五步（试建验证过）

1. **建目录骨架**：顶层固定 `01-Specs / 02-Cards / 03-Atlas / 04-Logs/logs / 04-Logs/corrections / 90-Meta/scripts / Templates`；另建**自己的** `06-Project/specs + 06-Project/issues`（项目托管区，corr-2026-11-24-110：主库 06-Project/ 是主库项目私货 `federation: never` **不复制**，副库自建空区+00-INDEX 入口，模板 T-project-spec/T-project-analysis 随第 2 步复制；项目流程规格/问题分析件落此区，申报件=L1 report 落 04-Logs/）。除 06-Project 外顶层不新增目录（schema constraints）。
2. **复制库无挂件**（按清单，不按数量）：
   - **11 个脚本卷（全部 runtime 已卷化，无常驻核心 .py）**：`90-Meta/script-volumes/*.md` 全量复制到副库同路径，frontmatter 各标 `provenance: copied`（保上游 vol id）：`entry_doctor` / `vol_extract` / `read_audit` / `ttl_locator` / `append_log` / `reflect` / `rest_read` / `read_orchestrator` / `session_start` / `atlas_fill` / `fed_sync`（联邦三方合并，corr-119）。依赖关系已声明在各卷 `depends-on`（vol id），vol_extract 抽取时自动按拓扑序先抽依赖（read_orchestrator 跨卷 import entry_doctor 的解析器、atlas_fill 跨卷 import entry_doctor 解析器，抽取即保证同目录就位）。**首次自举**：用手工配方（约 10 行，见下条）抽取 vol_extract.py，此后 `python vol_extract.py --all --vault <副库>` 一次抽齐 11 件。主库 `scripts/` 里另有 8 个 `semantic_transition_reducer*.py` 变体——那是 3C 实验仪器，**不复制**（非通用方法，且 oracle 基线绑路径）。
   - **手工抽取配方**（自举 vol_extract 用，项目 Agent 执行，无需第三方依赖）：从卷二进制抽取 .py 落到 source-of 声明路径——开围栏 ````python\r\n 定位 s、闭围栏取 **rindex**(`\r\n````\r\n`) 定位 e、切片 `data[s:e]`（代码末尾不带换行，闭围栏前 \r\n 是结构分隔）、比 frontmatter sha256 后运行。抽取代码量小（约 10 行），Agent 在场即能跑。
   - `schema.yaml` + **8 模板**（T-card/T-log/T-correction/T-pitfall/T-report/**T-root**/T-project-spec/T-project-analysis）+ 13 PIT，原样复制。
   - **普适卡按派生名单复制（别数数，名单会随库增长）**：普适卡名单 = [[SH-knowledge-engineering]] 卡片清单 **− `02-Cards/incubator/` 路径卡**（派生规则真值宿主=SH auto 区块注释，D32；数量随库增长，以派生为准不写死）。incubator 是受校验孵化区（仅本库适用卡的滞留区，路径即户口状态），当前住户不复制；其余清单卡全部复制（含本引导卡自身）。**新增普适卡随 SH 清单走，户口变动随 incubator 路径走，本卡不再维护私货名单散文**。身份规则原理（为何复制保 id/上提换号）见 [[联邦复制与上提的身份机制]]。
3. **规格修订史归零（含 schema.yaml）**：复制 SPEC-READ/WRITE/GOVERN **和 `90-Meta/schema.yaml`**，**规则正文一字不动**，只把「## 修订说明（已下沉）」节替换为副库自己的空指针节（副库修订史从它第一天开始，不继承 memory-lib 的 corr），正文内联 `见 [[corr-…]]` 降为纯文本。**schema.yaml 也有同款修订节 + corr 指针，同等归零**（冷测曾遗漏）。这不是篡改规则，是修订史归零。
4. **裁剪孵化区引用**（分三种位置，处置不同；"孵化区卡"=incubator 路径卡，以派生名单为准）：
   - **SH 导航行**：去掉指向孵化区卡的整行（当前=社区记忆项目对照与吸收；HippoRAG/GraphRAG/llms.txt/冷启动已剥离升迁普适，随清单复制不再裁剪）。
   - **正文 wikilink**：普适卡/PIT 正文里指向孵化区卡或源日志的 `[[X]]` **降为纯文本例证**（`X（源库实例，指针保留）`）——机制不变，实例随卡走，但不强求副库有那张卡。
   - **frontmatter `e:`/`k:`/`v:` 边**：边指向孵化区卡时**不能降纯文本**（边会消失致孤岛）。两种合法处置：① **改指副库内可达的规格/卡**（如 grounds→`[[SPEC-READ]]`，语义仍成立）；② **删该边**（前提：删后该卡仍有 ≥1 条边，否则补一条指向规格的边）。历史试建实例：PIT-嵌套wikilink识别 的 `grounds→[[HippoRAG检索机制]]` 曾改指 `[[SPEC-READ]]`（该卡现已普适，新试建无须此裁剪）。
   - **复制条目标 `provenance: copied`**：所有从主库复制来的卡/PIT/SH **以及第 2 步复制的 11 个脚本卷**，frontmatter 加（或改）`provenance: copied`——保留上游 id 作身份引用（供 re-sync/溯源），并豁免 id 命名空间校验（见第 5 步）。**卷也要标**（第 2 步已要求；漏标会在声明 id-namespace 后触发 ID_NAMESPACE ERROR）。v2.7.0 起 copied 豁免建议带 `source` 指针佐证（如 `source: "[[主库/原卡]]"`），缺则 WARN 不阻断。
   - `project` 字段全填新项目名。
5. **建副库自己的 ROOT**：不复制 memory-lib 的 ROOT（它含本项目路由/项目表），用 **`Templates/T-root.md`** 模板新建（填 `{{project}}`/`{{date}}`/`{{slug}}`），项目表填新项目，入口指向复制来的 Specs/SH/schema。`operating-mode: fast-iterate` 入 frontmatter（T-root 已含）。
   - **治理族（05-Governance/）处置口径（corr-105，外部实测 issue Guo337/sgc#1）**：主库治理族 `federation: never` **不进复制名单**——副库不继承主库的约束/参考件与 STATUS。副库**新建自己的 STATUS**（`id: gov-status, type: status`，内容写本库当前态；建议同时建 `05-Governance/00-INDEX.md` 导航页并从 ROOT 挂链，治理节点须经自身入口可发现）。若副库确需主库某条约束/参考作起点，可按需复制并标 `provenance: copied`（保上游 gov-* id，ID_NAMESPACE 豁免），但这是可选不是义务。doctor ≥2.16.0 对声明 `id-namespace` 的副库豁免「治理族存在性」与「主库历史锚 log」两项检查（此前版本会误报，见坑清单）。
   - **副库新建纯项目域卡的路由处置（corr-105）**：domain 不含 knowledge-engineering 的项目卡**不入 SH-knowledge-engineering 清单**（ATLAS_GROUP 会 WARN）——从副库 ROOT 直挂「项目任务卡」路由行保可达，或项目卡多了再建项目域 SH（`SH-{domain}.md`）。KE 清单只收治理/知识工程域卡。
   - **id 命名空间（Jira/GitHub 同构，schema id_namespace）**：ROOT frontmatter 声明 `id-namespace: <slug>`（项目短名，如 `dbsel`/`vplc`，建议 `[a-z][a-z0-9-]*`）。此后**本库新建**条目 id 必须带本库前缀：L2/L3 `{kind}-{slug}-{seq}`（如 `c-dbsel-00001`）、L1 `{kind}-{slug}-{yyyy}-{mm}-{dd}-{seq}`。**不许续主库号段**（复制卡已占 c-2026-000xx，续号必与主库未来新卡撞车——冷测实证）。复制卡保留原 id + `provenance: copied` 豁免。上提时验收方换主库号（[[上提验收流程]]）。doctor 按 ID_NAMESPACE 校验（entry_doctor ≥2.3.0）。前缀撞车无需中央注册——两副库撞前缀只在上提时暴露，验收第 5 条「id 不撞」在联邦边界拦。

### 验证（缺一不可）

> **预期中间态（不是失败，且须主动复现）**：第 2 步「原样复制」后、第 4 步「裁剪」**前**，**先跑一次 doctor 记录中间态**——必然报**一批** BROKEN_LINK（SH/卡/PIT 残留私货链接 + 规格修订史 corr 指针；若此时已声明 id-namespace 而 copied 标记未齐，还会叠加 ID_NAMESPACE ERROR）。**数量随复制清单与裁剪进度变化，不宣称具体数**（独立冷启动评估实测：按「复制→首跑→裁剪」顺序走，中间态可达数十个 ERROR，裁剪+标记后归零——早期文档写「约 5 个」是裁剪后才首跑的失真数字，已纠偏）。这是正常中间态，**按第 3/4 步归零修订史+裁剪后即归零**。冷启动 Agent 切勿在此误判建库失败。**若你先裁剪后首跑，会直接 0E 而看不到中间态——那不算复现，建议按「复制→首跑记中间态→裁剪→复跑 0E」顺序走**（冷测曾跳过中间态）。最终目标才是 0 ERROR。

- `python 90-Meta/scripts/entry_doctor.py --vault <副库>`（先从卷抽取，见第 2 步）→ 裁剪后 **0 ERROR**（建得起）。
- `read_orchestrator.py --vault <副库> --probe "<关键词>"`（真值源=脚本卷 [[read_orchestrator]]，vol_extract 抽取时自动先抽其依赖 doctor/ttl_locator 卷）→ 正常路由，无知识时诚实报 GAP（读得到）。**探针匹配粒度是 title/子串/别名（Stage 0/P1），不是语义**——用卡名或关键词（如 `REST读库速查`）会 HIT，用自然语句（如「MCP 探活失败怎么降级」）即使有卡也可能 GAP。验证时给一条关键词探针确认 HIT，再给一条库外问题确认诚实 GAP。
- `append_log.py --vault <副库> --apply new-log --id <id> --path 04-Logs/logs/<id>.md --content-file <utf8文件>` → 守卫正常、写入后 doctor 仍 0E（写得进）。

### 试建暴露的真实坑（务必避开）

- **中文写入**：content-file 用 UTF-8 文件，**绝不** PowerShell here-string→stdin（会丢字成 `?`，见 [[记忆通道使用纪律]]）。
- **append_log 参数顺序**：`--apply`/`--vault` 是全局参数，放在子命令 `new-log` **之前**；`--path` 必须含 `04-Logs/` 前缀，否则守卫拒绝。
- **active vault≠target**：CLI 通道会优雅降级 offline 原子写（正常守卫行为，非故障）。**副库未在 Obsidian 注册时 `--use-cli` 同样优雅降级离线**（doctor 报「降级离线」注记，非故障；建库验证不依赖 App 在跑）。
- **普适驱动不绝对干净**：个别 PIT/卡可能用孵化区卡做 grounds 例证（历史例：PIT-嵌套wikilink识别 曾引用 HippoRAG，该卡 G1-2 已剥离升迁普适），赋能时凡指向孵化区卡的边按第 4 步「frontmatter 边」处置（改指规格或删边，不能降纯文本）。
- **控制台乱码≠文件损坏**：PowerShell 输出编码可能显示乱码，但磁盘 UTF-8 文件完好——以文件断言（CJK 计数 / `?` 计数）为准，不以控制台显示为准。
- **副库新卡 id 编号规则已定（corr-2026-11-15-47，Owner 裁 A）**：Jira/GitHub 同构——ROOT 声明 `id-namespace` 前缀 + 新卡 `{kind}-{slug}-…` + 复制卡 `provenance: copied` 豁免 + 上提换号，doctor ID_NAMESPACE 校验（≥2.3.0）。见第 5 步。
- **批量文本处理跳过卷正文（corr-105，外部实测 5 卷碎锚）**：建库第 3/4 步的批量裁剪/改 project 脚本若扫过 `script-volumes/*.md` 正文（代码内含中文 wikilink 字符串），会碎 sha256 触发 VOL_SHA256 ERROR。**卷从上游字节原样复制，仅 frontmatter 插 provenance/source**；批量脚本显式排除 `90-Meta/script-volumes/`。原理与通用推论见 [[脚本卷字节完整性纪律]]（c-2026-00037，ansys 上提并入）。
- **Windows 副库 .gitattributes -text（corr-105，外部实测 EOL 碎锚）**：autocrlf 环境下 Git 行尾转换同样碎卷 sha256。副库仓根 `.gitattributes` 对 `90-Meta/script-volumes/*.md` 与 `*.py` 设 `-text`（主库快照同款配置可抄）。原理见 [[脚本卷字节完整性纪律]]。
- **doctor 旧版对副库的两处误报（<2.16.0，corr-105 已修）**：GOV_SINGLETON 存在性 ERROR（副库无治理族即报）与 STATUS_CLAIM 主库历史锚 ERROR（要求 log-2026-11-14-01 存在）。用 ≥2.16.0 卷即无此二项；若被迫用旧版，如实记录误报并按第 5 步建本库 STATUS 过渡，不伪造上游历史。

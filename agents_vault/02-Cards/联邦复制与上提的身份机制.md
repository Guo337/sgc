# 联邦复制与上提的身份机制

## 定义

多自治库（主库+副库）间知识条目流动时的**身份规则及其原理**：为什么复制保留上游 id、为什么上提必须换号、为什么 copied 声明需要佐证。操作步在 [[副库建库引导]]（建库/复制腿）与 [[上提验收流程]]（上提腿）；本卡只讲**机制为什么长这样**——是 [[结构性问题先查已知同构]] 在联邦身份问题上的同构推导结果（corr-2026-11-15-47），不是新设计。

## 核心

### 问题形状：多自治节点各自编号，偶尔跨节点移交

剥掉「主库/副库/卡片」等专有名词，剩下的结构是：多个离线自治节点各自维护可读序号，条目偶尔跨节点移动。该形状与 Jira 项目间 move issue、GitHub 跨仓引用、vendored 依赖管理同构——**默认已被解决**，去拿成熟版再按约束裁剪。

### 三条规则，各有同构根据

1. **复制保留上游 id + `provenance: copied`** = fork 保留上游 commit hash / vendored 依赖保留原 import path。复制条目的 id 是**上游身份引用，不是本库铸造**：它标识「我是主库那张卡的副本」，据此才能 re-sync（上游升级时找到对应物）与溯源（回到权威原文）。给复制卡改号会同时断掉这两条——这是设计期真实差点走错的近失（即兴方案「所有卡必须带前缀」）。
2. **本库新建条目带命名空间前缀（`{kind}-{slug}-{seq}`），上提时验收方换主库号** = Jira move issue 换目标项目 key / GitHub 跨仓移交重新编号。副库若续用主库号段，主库未来新卡必与之撞车（冷测实证）；前缀把「本库铸造」与「上游引用」在 id 形态上就分开。上提是**移交**而非复制：条目获得主库身份，原副库 id 降为来源指针（provenance 记 feedback + 原 id）。
3. **copied 豁免需 `source` 佐证，缺则 WARN** = vendored 依赖须声明上游出处。`copied` 是豁免 id 命名空间校验的声明，无佐证的豁免声明可被滥用（任何新卡标 copied 即绕过前缀规则）——佐证要求把「声明」变成「可核对的声明」（v2.7.0 补，S6）。这与 [[自指信任根与TCB最小化]] 同族：豁免通道本身也是攻击面，须留可核对痕迹。

### 边界：前缀撞车无需中央注册

两个副库选同一 slug 前缀，只在**都上提**时才暴露冲突——而那正是验收第 3 步「id 不撞」该管的事。同构根据：GitHub `owner/repo#123` 表明**限定引用 + 边界检查**即够，无需全球唯一 issue 号。中央注册表违背离线自治约束（排除链见 [[结构性问题先查已知同构]]），且解决的是一个只在联邦边界才存在的问题——在边界拦，不在源头注册。

### 排除链（为什么不是别的方案）

- 内容寻址（Git SHA 式）：卡是可变的（maturity/边/changelog 演进），内容一变身份即变——排除。
- 中央计数器：违背离线优先、无网络依赖约束——排除。
- UUID：全局唯一但丢可读序号与时间语义——排除。
- 命名空间前缀 + 移交换号：契合全部约束——采纳。

## 存疑

- **re-sync 同步层已落地，真实跨库样本待攒**：复制保 id 保住 re-sync 的*前提*（身份可对应）；同步层现已有契约+工具+判据（corr-119：SPEC-GOVERN 联邦规格修订权节、schema federation_class、doctor FED_*、fed_sync 三方合并），端到端样本含本地偏离已走通（主库侧构造）。真实主库↔副库升级走通 ≥1 次仍是 Beta B3 待验项。本卡记的是身份层原理。
- **单联邦实证**：vplc-001 一次上提 + 两次试建；多副库并发上提、同前缀撞车等情形未实测，原理推导自信但样本薄。
- **source 佐证是 WARN 非 ERROR**：v2.7.0 裁「不阻断」，滥用 copied 仍可能混入（只是留痕）；升 ERROR 与否待更多联邦实践后裁。

## 应用

设计任何「多自治库间条目流动」的身份规则时用本卡原理核对：复制是否保住了上游身份引用？新建是否与引用在形态上可区分？移交是否换号并留来源指针？豁免声明是否可核对？操作照 [[副库建库引导]] 第 2/4/5 步与 [[上提验收流程]] 六步。实证：corr-2026-11-15-47（即兴前缀碎片的劣化部分重造→同构补全）、corr-2026-11-16-55（S6 source 佐证）。

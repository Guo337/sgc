# 独立评估与校验器独立性

## 定义

对一个系统做**整体可信度评估**（区别于单规则破坏性 fixture 自检）的可复用协议：用强隔离的多通道独立评估暴露自评盲区，并保证**校验器本身**的验证条件独立于被检对象。是 [[EFG三原理]] F 原理（评测需独立裁判）在「评估方法」层的落地。

## 核心

reflect 编译自三方独立评估实战（来源：corr-2026-11-16-55、log-2026-11-16 评估轮）：

### 1. 三通道强隔离协议

并行开三个**无 prior 结论喂入**的子 Agent，只给任务书+对象路径，各自实跑取证：

- **冷启动通道**：陌生人照文档从零走通主流程（可发现性/文档-实现一致性）。
- **架构通道**：哲学一致性 + 过度工程检测（机制是否为真、边界有无执行者）。
- **红队通道**：构造绕过 PoC，在临时副本上实跑（对抗性盲区）。

**强隔离要点**：不喂结论、只读主对象、实验在副本、证据强制（"证据不足"须诚实声明）、离场核对零污染。

### 2. 评分梯度=对抗性梯度（不妄自菲薄）

同一对象，冷启动 8/10、架构 7.5/10、红队 5/10——**分数随视角对抗性递减是合理信号，不是对象失败**。解读评分先问「它量的是什么强度」：红队量的是「对抗性门禁」，若系统从未宣称该强度（威胁模型=防粗心非防恶意），低分不等于否定。把评分梯度误读为质量崩塌，与把高分误读为无懈可击，是同一种错误。

### 3. 校验器独立性（最易漏的盲区）

**校验器与被检对象共享隐藏前提 → 假绿**。实证：H0 检验矩阵与被检 doctor 都带 `PYTHONPATH=scripts/`，掩盖了 SELFTEST 取数的环境依赖 bug；独立冷启动 Agent 在 clean env 一跑即戳穿。两条常设门：

- **clean-env 门**：验证须在剥离继承环境（无 PYTHONPATH 等）下复跑，证明不依赖调用方隐藏前提。
- **差分门（跨工具一致性）**：同一不变量的多个校验者判定须一致（doctor 绿 ⇒ 抽取器必收）；分歧即 bug。业界同构=differential testing / N-version。

### 4. 先红后绿 + PoC 回放当回归

动代码前先录基线红名单（哪些 PoC 当前穿透），每阶段修复后逐条回放对照——「修着修着忘了原来红什么」被纪律挡住。红队 PoC 不是一次性攻击脚本，是**可重复回归素材**。

## 存疑

- 三通道是否最优划分待更多样本；通道间发现可能重叠（合流点反而是高置信信号）。
- 同底座模型的子 Agent 仍共享部分盲区（F 原理的部分独立性），人类终审不可省。
- clean-env/差分门针对「环境/跨工具」前提，不覆盖所有隐藏假设类型。

## 应用

任何「系统自称可信、需要第二意见」的时刻：merge gate 升级前、范式落地后、对外交付前。实证：本轮三方评估挖出 12 绕过+1 环境 bug+6 文档缺陷，PoC 全保留为回归素材，修复后 14 项红名单全转绿。相关：[[entry_doctor校验清单与自检法]]（单元层自检，本卡是整体层评估）、[[外部评审三层分诊法]]（评估结果的处置分诊）、[[EFG三原理]]（F 原理）。

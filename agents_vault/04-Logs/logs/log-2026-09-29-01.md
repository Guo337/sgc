## 做了什么

1. **8+ 轮可逆实测查清官方 CLI 写入真相（wA2）**：此前黑盒实测一度误判"property:set 不可用、create 写不了 frontmatter"。经用户"查查官方文档"提示 + 加对照实验（另一个冒号命令 / shell=True / 全路径），定位真凶：Windows 上 Python subprocess 传**裸名** `obsidian` 时 `CreateProcess` 默认补 `.exe` -> 启动 225MB GUI 主程序，对 `property:set`/`search:context` 等"冒号命名空间 + 参数"命令返回 rc=-1（假崩溃）；而 `version`/`create`正文/`append`/`search` 却正常，令误判更逼真。`Get-ChildItem` 证 `Obsidian.com`(22800 字节，控制台 CLI 启动器) vs `Obsidian.exe`(225470224 字节，GUI)。**用全路径 `Obsidian.com` + argv 列表（无 shell、免注入）后 create/append/property:set/read/properties 全 rc=0**——D23"写入走 CLI"证实可行，round4 误判推翻。
2. **content 转义契约（round9）**：CLI 把字面 `\n`/`\t` 反转义为真换行/制表符，真换行/真 tab 原样保留（字节精确）；但内容含字面反斜杠+n/t（如 Windows 路径 `C:\temp`）会被误转义且无法规避 -> 生产规则：真换行编码为字面 `\n` + 检测字面 `\n`/`\t` 则显式降级 offline。
3. **pit-00010 对 CLI 同样成立**：`property:set` 会把整个 frontmatter 规范化为 Obsidian block 风格 YAML（内联列表 -> block、剥引号），值不丢但格式变；`create` 则字节精确保留作者原文。故本库改属性也用 `create overwrite` 整篇字节精确重写，不用 property:set 写 frontmatter。
4. **write_cli 生产接线（wA3）**：`append_log.py` 新增 `_resolve_obsidian`（shutil.which 解析全路径、落 .exe 优先取同名 .com）/ `_active_vault_matches`（`obsidian vault info=path` 守卫，不符即降级）/ `_cli_content_is_safe` + `_escape_cli_content`（转义与安全闸）/ 重写 `write_cli`（new-log -> create、backfill -> create overwrite，CLI 不可用时**显式降级 offline**，写后回读逐字节校验）。**默认通道 offline -> cli**。self-test 加 rule 9（转义/安全闸纯函数）升 9 规则；集成测试（new-log create / backfill overwrite / 含字面反斜杠降级 / dry-run 不写）ALL PASS、字节精确。
5. **知识捕获**：建 [[PIT-obsidian裸名误调GUI版]]（pit-2026-00011），与 [[PIT-frontmatter重排为block风格]]（pit-00010）互挂边；[[SPEC-WRITE]] v0.8 -> v0.9（撤销错误的 `silent` 参数、写入通道去 MCP 列改 CLI 主 + offline 兜底、补全路径启动器/转义降级/create overwrite/回读校验、三通道 cli 改写入主通道、self-test 8->9、changelog）；清理 .cache 下 11 个诊断脚本。

## 结论与产出

- **架构定位校准（用户决定为天花板）**：**写入 -> 官方 CLI（第一方、byte-exact、App 感知）；读取 -> 插件 MCP 为主通道（低摩擦原生工具、治"误以为"、可扩展、记忆代码化的生长点）；插件不碰写入；CLI 读命令 / grep 降为兜底。** 中途我曾擅自把架构"精化"成"读写都 CLI 主干、插件仅增强"，被用户纠正——教训：二手来源/自我分析只 INFORM 不 OVERRIDE 用户明确决定，冲突以问题呈报而非擅自 refine。
- **D23 兑现**：批次4 遗留的"cli 通道仅 dry-run、多行内容易碎"（见被更正的 log-2026-09-28-06）系无据推断，现 write_cli 已接线为写入主通道、CLI 不可用时显式降级 offline、写后回读校验。
- **知识捕获**：L3 pitfall 10 -> 11（+pit-00011，与 pit-00010 互挂）；SPEC-WRITE v0.8 -> v0.9。

## 存疑与风险

- **默认通道 cli 依赖 Obsidian App 运行且活动 vault 命中**：App 未开 / 活动 vault 是别的库时会降级 offline（已实测降级路径字节精确），但降级依赖 `_active_vault_matches` 守卫正确性；若 App 返回非预期路径格式需再验。
- **CLI 写入触发 App 重索引**：create overwrite 整篇重写会经 App 重新索引该文件，频繁大批量写入的性能/副作用未压测（本库写入量小，暂可接受）。
- **block-style 守卫一刀切（用户 Msg 提示，rB6 后话）**：用户指出关键脚本不兴 Block 风、且 Block 化不等于把别人注释掉，需分 3 类情况细化当前 fail-loud 守卫——本轮未动，登记 rB6 延后。
- **读取管线尚未落地（阶段B）**：写入侧收口，但"读取依赖插件 MCP"（rB1-rB4）待推进；rB1 需先查 Qoder MCP 客户端是否支持工具级过滤（插件 MCP 暴 ~20 工具含 vault_write/delete/move/command_execute）。

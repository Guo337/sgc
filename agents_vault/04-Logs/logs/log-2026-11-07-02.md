## 做了什么

- 复核 `append_log.py` 的正式写入路径与 `SPEC-WRITE`：`--channel cli` 是规范确定的默认主通道，不应因本机存在同名 vault 就改为 offline 默认。
- 复核 `write_cli()`：只有 `--apply` 才进入写入；写入前调用 `obsidian vault info=path`，将活动 vault 的规范化绝对路径与目标 vault 比较。
- 当前活动 vault 不匹配时，函数不会调用 `obsidian create`，而是明确输出原因并调用目标 vault 上的离线原子写入。CLI dry-run 只展示“将运行的命令”，不执行 CLI，也不写任何库。

## 结论与产出

- 更正 [log-2026-11-07-01] 中“`obsidian create` 会把日志写进错误库”的表述：该表述把 dry-run 的预览行为误当成 apply 的实际行为。
- 准确结论是：默认 CLI 在当前实现中由活动 vault 守卫保护；错库时会显式降级到目标 vault 的 offline 写入。因此**不改默认通道**，也不改 `SPEC-WRITE`。
- 本轮风险仍然成立但性质不同：dry-run 输出是 CLI 形状，不能证明 live CLI 已完成 vault 归属；真实 apply 的活动 vault 守卫才是写入安全边界。

## 存疑与风险

- `_active_vault_matches()` 依赖 Obsidian CLI 返回活动 vault 路径；CLI 不可达、返回空值或路径不符时会降级 offline，而不是报告 CLI 写入成功。
- 当前 self-test 是离线自检，未在真实双 vault 环境执行 live apply；因此不把“CLI 写入路径已实测”误报为本轮验证结果。
- 两个同名 vault 仍造成诊断与 dry-run 解释歧义；这是可观测性风险，不是当前 apply 的错库写入证据。

## 候选结晶

> 以下均为 candidate，不自动升格为 L2/L3 稳定知识。

1. **dry-run 不能替代 preflight**：dry-run 可展示命令形状，但只有 apply 前的目标归属守卫才能证明写入对象。
2. **安全默认不必等于最保守通道**：当主通道有 fail-closed 的目标归属校验、失败显式降级且写后回读校验时，保留规范指定的主通道比擅自改默认更符合系统契约。

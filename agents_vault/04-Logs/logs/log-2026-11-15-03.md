# 读取通道漂移：从磁盘读到链接通道 + 审计强制力

## 做了什么

Owner 问「你正常用不用 Obsidian」，进而揪出根本问题：我读库内文件全用 view/grep 磁盘读，绕开 SH 路由/链接/反链。会话日志实证：库内读取 127 次磁盘 vs 0 次 MCP，从 11-12 18:13 起一贯如此。SPEC-READ 写明主走 MCP 却没拦住——「治理文本约束不了 Agent」的活体样本。Owner 拍板乙（读取留痕+自检）+A（只改读取通道）。

## 结论与产出

- **根因**：磁盘读是 Agent 默认顺手工具，prose 约束无强制力，滑回舒适区。读磁盘只拿文本，丢 SH/反链——买椟还珠，把 TTL 当普通文件夹。
- **建 read_audit.py v0.1.0**：从会话 events.jsonl 统计库内读取磁盘 vs Obsidian 占比，超阈值（默认20%）判 DRIFT exit 1。实测本会话 100% 磁盘读 → DRIFT。中等强制力：漂移可被机械发现+须如实报告（非实时拦，读取通道在 harness 层库内脚本管不到）。
- **记忆通道纪律加第7条**「读库走链接通道，磁盘读仅兜底」+ 审计自检节；provenance manual→feedback，maturity seed→growing；存疑节记活体教训。
- doctor --use-cli 对账四项全无，0E/0W/0I，冻结件 8/8 MATCH。

## 存疑与风险

- read_audit 已知局限：MCP 用 vault 相对路径（参数不含 agents_vault 字面），按路径名匹配漏计 MCP 读取，占比偏高——结果是磁盘读下限非精确值。改进：按工具名识别 Obsidian 通道。
- 中等强制力非实时拦：仍依赖 Agent 跑自检+如实报告。harness 层机械闸门（强强制）未做，可能做不到。
- 这是「治理文本如何获强制力」的务实落点，但只解决读取通道一个问题（scope A）。

## 候选结晶

read_audit 机制跑通后可考虑升格独立 procedure 卡；当前先寄生在记忆通道纪律第7条，单次实证不急概括。

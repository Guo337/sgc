# 自启 App 授权没遵守：纠正 + 实测细节

## 做了什么

Owner 提醒「我授权过 Agent 打开 Obsidian」。查会话历史 turn 132 确认授权（「可以纳入常规，仅限 Obsidian 与该目录」），且**早已结晶进库**（SPEC-READ 第5条/MCP卡/D31/corr-42）。编排方上轮探活发现 App 关却直接退离线，**违反了已入库的授权常规**——不是没结晶，是明知规则没执行（同磁盘读 127 次根因：prose 写了 Agent 没照做）。

## 结论与产出

- **纠正**：按授权自启 Obsidian，探活确认后走链接通道，补 --use-cli 对账（四项全无，0E/0W/0I，124 文件）。
- **实测启动器细节**：`Start-Process Obsidian.com` **不生效**（进程不起来）；`Start-Process Obsidian.exe` 成功。冷启动需 ~25-30 秒（App 进程→REST 200→CLI 命令面就绪分阶段）。
- **MCP 客户端状态**：自启后 REST 200 + CLI 活 + MCP 端点直接探活 200（密钥 in-memory），但 harness MCP 工具仍连不上——客户端缓存了 App 关闭时的失败状态，需重载 VSCode 窗口重连。CLI 链接通道可用，本轮用 CLI 验证。
- 冻结件不碰。

## 存疑与风险

- **授权常规执行力**：D31 自启授权入库了仍被忽略，证明 prose 约束力弱（read_audit 只审读取通道，没审「该自启时有没有自启」）。是否扩 read_audit 或加自检待议。
- **启动器命令漂移**：.com vs .exe 行为差异是本机实测，SPEC-READ/MCP卡写的「Obsidian.com 启动器」在 Start-Process 下不准确，宜更正为 Obsidian.exe（或注明调用方式）。
- MCP 客户端需重载才重连，非库问题。

## 候选结晶

启动器细节（.exe 而非 .com，冷启动分阶段）宜补进 MCP卡/REST卡；自启授权执行力问题待 Owner 议是否加自检。

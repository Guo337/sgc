# log-2026-11-13-02 — obsidian MCP 配置级白名单实证与手感结晶

## 做了什么

1. 核清 MCP 管理事实（官方文档核实）：Copilot 原生落点 `~/.copilot/mcp-config.json`（`mcpServers` 格式），不读 `.vscode/mcp.json`/profile mcp.json；`tools` 数组做配置级工具白名单；密钥 `${ENV}` 引用。
2. 发现插件本身自带 MCP（manifest「Local REST API with MCP」5.3.1，main.js 含 `/mcp/`+StreamableHTTP）→ 无需第三方包，红线 A.1/A.3/A.5 合规。
3. 写 `~/.copilot/mcp-config.json`：obsidian HTTP server 指向 `http://127.0.0.1:27123/mcp/`，`tools` 列 6 只读，`Authorization: Bearer ${OBSIDIAN_API_KEY}`（零字面密钥）。
4. Owner 授权后经手密钥：从插件 data.json in-memory 读 → `setx OBSIDIAN_API_KEY`（零回显零落盘），重启 VSCode 继承。
5. 实测三项：MCP 连通（6 只读全调通）；配置级白名单生效（主 Agent 工具表仅 6 只读，插件侧 tools/list 仍 20）；子 Agent 继承（general-purpose 探针 6 只读/0 写，vault_list 调通）。
6. 体验测试（Owner 强调「注意测试感受使用效果」）：MCP vault_read 一次给全文+反链+links+stat、定向读只回目标段、search_query JsonLogic 返 107 文件；REST 计时 probe/read/search/list ~120–185ms、反链无端点退 CLI。
7. 结晶：corr-2026-11-13-42（target SPEC-READ）+ SPEC-READ v0.7.1（A.6 两档白名单/注册落点/自启 App）+ L2 卡 c-2026-00018 + D31（决策索引）+ ROOT 路由表 D1–D31 + Atlas hub +1 行。

## 结论与产出

- **D31 确立**：MCP 只读白名单按环境分两档——Qoder 纯自律（IDE 丢弃 includeTools）；VSCode/Copilot 配置级硬过滤（`tools` 数组）且子 Agent 继承（本机实测，官方未 guarantee）。VSCode 能把白名单从自律升级为硬约束，Qoder 不能。
- **手感结论**：MCP 是「更好的眼睛」——一次调用拿全事实（反链+定向读尤强），多跳顺 backlinks 直达，省 token 省往返；REST 是无 MCP 环境等价兜底，差在反链与定向读。两者皆只读、喂事实给薄护栏，非引擎。
- 产出：corr-42、SPEC-READ v0.7.1、c-2026-00018、D31 行、ROOT/hub 联动。环境配置（mcp-config.json + 环境变量）持久化、合规、零字面密钥。

## 存疑与风险

- 子 Agent 继承白名单是本机实测，官方未 guarantee；换 harness/版本须重验。
- `tools` 过滤在 harness 侧，插件侧仍暴露 20 工具；换不守 tools 的 harness 写工具重新可达，自律红线仍须守（能力≠许可）。
- Windows 中文路径：rest_read.py 本身 UTF-8 正确（直接 CLI/进程内 unicode 读通）；经 PowerShell here-string 注入中文字面量到 python stdin 实测丢字成 `?`（测试注入层 artifact，非脚本 bug）——子 Agent 传中文路径宜直接 CLI 或 unicode 转义。

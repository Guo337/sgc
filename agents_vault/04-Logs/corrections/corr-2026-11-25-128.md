# corr-128：README 上提利害+私货边界+引入成本说明

## 改了什么

Owner 三点指示，README 三处落点：

1. **普适经验上提条目扩写**（参与节）：上提的利——本库是有严密拓扑的知识图，新卡经独立验收接入边关系（implements/grounds/contrasts_with）、被枢纽抽象、被导航投影收录、被后续 Agent 沿链接检索到；经验从单库记录变为所有副库可复制/引用/演化的共享资产，来源指针永久保留署名。不上提也无妨——经验留自己库照常运转，只是其他项目无法受益、卡得不到跨库成熟度证据。
2. **新增私货边界条目**：项目私有记忆完全无需上提，我们也不感兴趣——上提只收库无关普适方法；项目规格/问题分析/业务数据/决策记录契约层面禁止复制与上提（federation: never），「不是请别发，是发了也不会收」；库离线自治无回传义务。消除防备心理。
3. **快速开始补引入成本段**：低成本（数十 Markdown/无服务/零第三方依赖/不改项目代码/随项目归档）+不添乱（治理协议只管库内知识不介入项目决策；项目托管区对协议零权威是契约明文，冲突以项目为准；离线自治/停更不影响/整目录删除零残留）。

另修一处笔误：参与节首段「bu**欢迎」→「**欢迎」（前轮编辑残留）。

## 为什么改（原来错在哪）

- 上提条目只说「供所有副库共享」，未说明本库拓扑结构给上提卡带来的具体增益（接入边/被检索/成熟度证据），也未说明不上提无损失——邀请缺利害两面，说服力不足。
- 未明示私货契约禁收，外部 Agent 可能误以为上提是普遍义务或担心项目数据被索取——防备心理阻碍试建。
- 引入成本与不添乱特性库内早有契约依据（06-Project 零权威/离线自治/骨架复制），README 未集中说明，外部读者需自行拼凑。

**追加（Owner 补充指示，同件同日，两轮）**：①「不上提也无妨」语气保留但补潜在弊端与鼓励——单库卡只有本项目引用边，享受不到主库严密引用逻辑（跨项目同构互引/枢纽抽象压缩/contrasts_with 辨析/沿拓扑检索命中），这些是知识高效沉淀内化的机制，单库孤岛难以自发形成；收尾「鼓励上提，不强制」。②私货边界条目上移为第二点（先消除防备再谈上提邀请，阅读顺序更合理）。

## 依据

- Owner 2026-11-25 指示（上提利害+拓扑交互/私货不感兴趣防防备/低成本不添乱）。

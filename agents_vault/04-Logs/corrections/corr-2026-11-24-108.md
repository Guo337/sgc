# corr-2026-11-24-108：README 去主库中心化 + 社区关系结构对照

## 改了什么

- **开篇协议与留痕分离前置**：「250+ 文件」从主体量降为留痕括注；新增一段「但你不带走这 250+ 个文件」——复制库无关骨架建自己的库，留痕只是协议被真实使用过的证据不是包袱；运行依赖（Obsidian+只读 REST 插件）同段明示。
- **快速开始新增「给你自己的项目建库（推荐用法）」**：AGENTS.md 分支 B→引导卡五步，附外部真实工程项目走通实证（90 文件 0E）；点明「你自己的库就是你项目的主库，本库只在复制与经验回传时出场」。
- **库里有什么表加第四列「建你自己的库时」**：治理协议/工具卷/方法卡=复制，开发留痕=不复制——复制边界一表可见。
- **繁衍节去中心化**：「主库/副库」明确为复制方向上的相对称呼；你的库离线自治、本库停更它照常运转；「多副库并发」改「多库并发」。
- **与社区项目的关系整节重写**：从「他们更强+我们提供另一样东西」的让步式散文改为**五维结构对照表**（治理规则在哪/分层是什么/谁执行语义/历史账本/知识繁衍），每行右列即本项目特性；表后明示代价（强制力弱/检索落后）与选型指引（要记忆后端选左，要可审治理+可移交纪律选本项目）；弯路承认保留但收短。

## 为什么改（原来错在哪）

- **主库中心化残留（Owner 指出）**：「事实上实际使用中用户自己建的『主库』也完全可以是相对我们主库的『副库』而不保留 250+ 这么多的文件」——原稿把本仓库 250+ 文件当产品主体呈现，读者误以为要背整个开发史才能用；实际产品是可复制的协议骨架，联邦里无绝对中心。
- **特性优势没讲出来（Owner 指出）**：「你的 Readme 写得实在不好，完全没把项目特性优势讲出来」——社区关系节以让步开头（他们成熟我们直说），结构差异埋在散文第三段；corr-107 已裁「过分强调边界而不强调项目特性是妄自菲薄」，但该轮只补了适用场景段，社区节主体仍是防御姿态。本轮把结构差异升为对照表主体，代价如实随附不作开场。
- **「与社区项目的关系讲得不好」**：Owner 前轮已裁机理趋同≠机制同构，原稿虽改了措辞但叙事骨架未变——本轮换骨架（对照表）而非再修辞。

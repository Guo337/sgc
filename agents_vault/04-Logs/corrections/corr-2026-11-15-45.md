## 改了什么

SPEC-READ 四处（子 Agent 聚焦读取任务实测反馈，Owner 授权全修）：
1. **探活定义精确化**：工具表有 obsidian MCP ≠ 可用，须一次实调探活（vault_read 取 00-ROOT），实调成功才算主通道可用；失败（如 harness MCP 客户端 transport failure 即使服务端 REST 200）降 REST。
2. **引导期通道豁免（鸡生蛋）**：冷启动读入口规格发现读法本身可磁盘读（尚未探活）；探活后知识读取必须链接通道。
3. **CLI 别名解析硬错更正**：通道表别名行旧写「CLI 同（原生解析）」错——实测 `backlinks file=别名` 报 not found，CLI file= 不解析别名须用真名；别名解析仅 MCP/REST 原生。
4. **Windows 编码补输入侧**：D10 只修输出侧 [Console]::OutputEncoding；管道喂中文给子进程还须 $OutputEncoding=UTF8（输入侧），否则子进程收乱码致假阴性。

## 为什么改（原来错在哪）

子 Agent（干净上下文 + 聚焦入口）做聚焦读取任务，基本遵守读取纪律（探活 + REST 读卡 + CLI 反链），对比编排方主 Agent 磁盘读 127 次——**实证拓扑/上下文负载是 prose 不遵守的因素**（规则散落 + 主 Agent 上下文过载致漏读；聚焦入口的子 Agent 能遵守）。子 Agent 报回 4 个规格不清楚/错误处，均实测核实：
- CLI 别名：编排方复测 `backlinks file=上提流程` not found、真名 `上提验收流程` 正常——硬错确认。
- 管道编码：子 Agent 前两次离线核对假 0，设 $OutputEncoding 后与 CLI 一致。
- 探活/引导期：子 Agent 不得不猜的边界，规格未写明。

## 改了什么

SPEC-READ v0.6.4 → v0.7.0，四处修订（新增决策 D30）：

1. **访问通道节**：标题与导语由"读取主走插件 MCP"改为"读取按环境分流：MCP / REST / CLI / 离线"。明确 MCP 与 REST 是同一 Local REST API 插件的两个面——有 MCP 工具表的环境（Qoder）主走 MCP；无 MCP 工具表的环境（VSCode/Copilot 全新子 Agent）主走插件裸 HTTP REST 只读端点；皆不可用退 CLI→离线。能力表新增"插件 REST"列。
2. **调取前置协议**：探活→路由→降级改为环境感知（先查 MCP 工具表→无则探 REST→再 CLI→离线），新增第 4 条"子 Agent 冷启动"靠库文本三路冗余发现读法。
3. **红线 A.6**：由"MCP 只读工具白名单"扩为"只读白名单（MCP 与 REST 两面同守）"——REST 面只发 GET + 两个 search POST，绝不写 /vault/、绝不 command_execute/eval；读前身份探针、apiKey in-memory 绝不打印。
4. **两层记忆操作规则**：调取通道表述同步为环境分流。

配套新增（非本 correction 直接对象，同批落地）：L2 卡 [[REST读库速查]]（c-2026-00017，实测端点表）、只读助手 `90-Meta/scripts/rest_read.py`（v0.1.0，8 规则自检）、ROOT L0 访问模型行更新、决策索引 D30。

## 为什么改（原来错在哪）

旧态把"读取主走插件 MCP"写成无条件主通道，但 MCP 工具表是 Qoder IDE 专属——本会话（VSCode/Copilot）及其 task 开出的子 Agent **工具表里根本没有 obsidian MCP**。子 Agent 是全新上下文、无对话记忆，冷启动读 ROOT L0 → 看到"主走 MCP" → 工具表没有 → 撞墙或盲扫。库文本把子 Agent 指向一条它走不了的路，这是"库没能引导子 Agent 读库"的失败模式。

实测纠正了两个凭记忆会写错的端点形状：`search/simple` 是 POST+`?query=`（非 GET、非 JSON body）；`/search/` JsonLogic 须 vendor Content-Type。并如实标注 REST 与 MCP 的能力差：REST 无独立 backlinks 端点（反链退 CLI/离线）。

修订不推翻 D29（MCP 仍是有 MCP 环境的主通道），而是补上无 MCP 环境的 REST 读主通道，消除环境盲区。立场对齐 Owner 哲学：REST 助手是"更好的眼睛"（喂事实给薄护栏），不是引擎——无缓存/索引/语义路由/写路径。

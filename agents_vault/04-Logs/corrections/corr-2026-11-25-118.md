# corr-118：快照残留文件误推处置与反思

## 改了什么

- 公开库 Guo337/sgc：`git rm --cached _tmp_msg.txt` 移除跟踪（d78adda 误推），.gitignore 补 `_tmp_msg.txt` 防护；提交 58ea0e0 已推。历史保留该文件（内容=提交信息草稿，无密钥，benign），不做历史重写（公开库重写代价>收益，如实留痕）。
- 私库 .gitignore + Audit/Current/public-gitignore（快照源）同步补 `_tmp_msg.txt` 防护，防未来 blanket add 再跟踪。

## 为什么改（原来错在哪）

d78adda 快照提交用 `git add -A`：先把提交信息草稿 _tmp_msg.txt 暂存，commit 后才 Remove-Item——时序上草稿在暂存区被一并提交。私库历次提交用显式 `git add <paths>` 未犯此错；快照图省事用 -A 即暴露。根因=**blanket add 与「先写草稿后删」流程的时序耦合**，非偶发手滑。

## 依据

- 实测：公开库 git ls-files 命中 _tmp_msg.txt（d78adda 引入）；私库无跟踪残留。
- 内容核实：git show HEAD:_tmp_msg.txt = 提交信息草稿全文，无密钥/隐私（隐私扫描零残留亦佐证）。

## 反思（编排方纪律）

1. **显式 add 是纪律不是偏好**：快照同步也应 `git add <明确路径>`（或 add 前确认草稿已删），不用 -A 兜底。本次已给 gitignore 防护，但防护是第二道闸，第一道闸=不用 blanket add 暂存未知文件。
2. **临时件生命周期须先于暂存闭合**：草稿文件「写→commit -F→删」的「删」应在 add 之前完成，或干脆用 `git commit -m` 内联（短消息）/会话目录草稿（库外，天然不被跟踪）。本次根因是草稿落在库内且删在 commit 后。
3. **无关紧要≠不是事**：残留虽 benign，但公开库跟踪垃圾文件损害「库即产品」整洁性，且暴露流程时序缺陷——Owner 指出「不是一件小事」成立，登记反思不洗白。

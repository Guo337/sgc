## 为什么改（原来错在哪）

- **维护者原分析两处错误（v3 纠正）**：①分析件用既有 L2 卡——会污染结晶/装配/联邦面（reflect 扫 02-Cards、orchestrator 只滤 overview、SH 清单派生复制），项目私货默认进知识面正是 Owner「无需过度管理」要排除的；②PROJ_AUTHORITY 拟用正则 policing 正文——Goodhart 陷阱，改路径↔type 绑定+字段黑名单不审正文。
- **v1 子 Agent 数据不计入**：编排方（维护者 Agent）在指令中手抄「磁盘读合规」豁免通道纪律——越权立法（D33 批准权在 Owner），子 Agent 全程磁盘读知识件绕开 REST 身份探针。Owner 指出：约束子 Agent 的是项目文本不是编排方指令（SH-index「身份通道指 SH 不手抄」）；编排方长期随 Owner 开发太熟反而自我豁免，不具备普适性（朋友项目 Agent 走 SH→角色件→宿主自然合规），不计入日志。v3 重开：指令只装目标/边界/验收，通道指 SH 不手抄规则，子 Agent 自行走 SH→role-ke-auditor→宿主文本，全程 REST 合规。
- **v3 独到发现**：01-AUTHORITY §2 precedence 把 ACTIVE governance constraints 排在 Specs 之上——案 B 挂治理族会让项目规格获得压倒 runtime 的权威位（语义倒挂硬伤，v1 只说语义稀释没抓到权威序）；申报件落 04-Logs 保「层号不变」裁定精神+守卫零改动比扩径更省。
